# Road Rash–Style Browser Motorcycle Combat Racer — v1 Plan & Progress

## Context

The user wants to recreate the classic mid-90s game **Road Rash** — a motorcycle racing game where you can punch and kick rival riders off their bikes — as a private, personal project for themselves only (not published). The goal is to relive the childhood experience of Road Rash's signature feature: full-contact combat racing. This is explicitly a **first development cycle**: a deliberately trimmed-down scope (one track, one bike, one avatar, 5 AI opponents, no health/damage system, no score saving, no manual transmission) with an understanding that maps/bikes/avatars/persistence/manual transmission are future additions once this core loop feels great. It must run entirely in the browser with **no install required to play** — Node/npm during development is fine, but the shipped result is a static site.

The core design tension resolved during planning: "very high graphics, absolutely realistic physics" is tempered into what's actually achievable and *fun* for a solo hobbyist build — stylized-realistic visuals (not photoreal) using free/open-source assets bundled at build time, and "arcade-sim hybrid" vehicle physics (the same category of physics real motorcycle games — including the original Road Rash — actually use), rather than research-grade real-world 2-wheel gyroscopic simulation.

## Confirmed Decisions

- **Camera**: third-person chase cam (spring-arm follow, collision-aware).
- **Visual style**: stylized realistic — strong lighting/shadows/post-processing (bloom, SSAO, motion blur) via Three.js. Custom-built road/terrain/scenery; free/open-source (CC0 or free-for-any-use) bike + rigged rider models/animations sourced from sites like Sketchfab/Mixamo/Kenney/Poly Haven, bundled into the build (nothing fetched at runtime, nothing the player installs). Specific assets will be picked and shown to the user before finalizing, during implementation.
- **Language/tooling**: TypeScript + Vite. Node/npm needed only for development; `vite build` produces a static site with no backend.
- **Physics engine**: Rapier (`@dimforge/rapier3d-compat`) — chosen over cannon-es for joint-solver stability (critical for ragdolls) and raycast performance with 6 simultaneous bikes.
- **Vehicle physics model**: arcade-sim hybrid — rigid-body chassis, 2 raycast wheels (front/rear) for suspension, realistic accel/braking/traction/grip-loss curves, visual-only lean into turns (chassis itself never tips from steering alone).
- **Track**: one fixed point-to-point road (not a loop) with curves and elevation, authored as a spline, ending at a finish line. Off-road (grass/dirt) has lower grip/higher resistance but no invisible walls or hard boundary.
- **Riders**: 6 total — 1 player + 5 AI. AI is "opportunistic": primarily races well, occasionally throws a punch/kick at a nearby rider (player or bot) when advantageous.
- **Combat**: shared hit-detection/knockback system used identically by player and AI. Punch (P) and kick (K), each with range/arc/windup/cooldown. Knockback impulse feeds directly into the fall system.
- **Falling/recovery**: physics-driven ragdoll on knockdown (fall distance/direction emerges naturally from momentum at impact, not hardcoded), settle → get-up animation → run to bike → remount → resume riding. Identical state machine for player and AI.
- **Controls**: WASD or Arrow keys (accelerate/brake/steer), P = punch, K = kick. Fully automatic transmission (RPM/gear simulated internally for engine sound/feel only).
- **Wrong-way**: hard block — cannot travel backward past a small tolerance.
- **No health/damage system, no score/progress persistence, no backend** in v1.
- **Graphics quality settings**: Low/Medium/High presets (shadow resolution, post-processing, draw distance/fog, pixel ratio, scenery/particle density), chosen once on the start screen before racing.
- **Race end condition**: race is live until the player finishes, OR a generous timeout elapses (~3x the winning bot's time, or a hard cap e.g. 6 minutes), whichever comes first. If the player times out, they're ranked last with a "Did Not Finish" end screen rather than Win/Lose.
- **Post-race**: end screen shows result (Win / Lose / DNF) + finishing position, with a "Race Again" button that resets everyone to the start line. Nothing persists across a page reload.

## Key Systems

**Physics loop** (`Game.ts`): fixed 60Hz accumulator for physics/AI/input/combat/ragdoll steps, decoupled from variable-rate rendering; entities interpolate between previous/current physics transforms each render frame to avoid stutter.

**Vehicle controller** (`physics/VehicleController.ts`): per-wheel raycast suspension (spring/damper from ray-hit compression), RPM/gear-lookup drivetrain feeding a torque curve, traction/slip model comparing drive force to available friction (road vs off-road via `TerrainMaterial`), hard reverse block, steering with speed-scaled effectiveness, cosmetic-only lean applied to the render mesh (not the physics chassis).

**Rider state machine** (`entities/RiderStateMachine.ts`): `RIDING → FALLING → RAGDOLL → GETUP → RUN_TO_BIKE → MOUNT → RIDING`, identical code path for player and all 5 AI riders (only the driver of RIDING/RUN_TO_BIKE targeting differs). `RagdollController.ts` builds a simplified 6–9 capsule-body ragdoll with joints on FALLING, drives the skinned mesh's bones from body transforms while active, and tears down back to animated mesh once settled.

**Combat** (`combat/CombatSystem.ts` + `combat/AttackDefinitions.ts`): punch/kick each define range, arc, windup/active/recovery timing, and knockback force/direction. A single hit-detection/knockback path is fed by both `PlayerController` (P/K key → attack intent) and `ai/CombatBehavior.ts` (opportunistic scoring based on proximity, alignment, per-bot aggression, and a player-bias so fights actually happen), so there's no divergent AI-vs-player combat code.

**AI driving** (`ai/DrivingBehavior.ts`, `WaypointPath.ts`, `AvoidanceBehavior.ts`): spline lookahead target + curvature-based braking for corners, per-bot randomized lateral offset so bots don't stack on one racing line, reactive lateral avoidance bias (suppressed against a bot's current combat target so it can close distance to fight).

**Track** (`track/TrackBuilder.ts`): `CatmullRomCurve3` from hand-authored control points → triangle-strip road + off-road meshes and matching Rapier trimesh colliders tagged with friction/grip data; `InstancedMesh` roadside scenery; sensor-collider finish line recording per-rider finish order/time without stopping the sim for others.

**Camera** (`camera/ChaseCamera.ts`): critically-damped spring-arm follow with collision-aware raycast pullback (reuses the same raycast primitive as suspension), speed-based pullback, subtle roll tied to bike lean, switches to follow the ragdoll pelvis during a fall and reattaches on remount.

**Graphics settings** (`settings/GraphicsSettings.ts`): Low/Medium/High presets controlling pixel ratio, shadow map on/off + resolution, which post-processing passes are active, fog/draw distance, and scenery/particle density — chosen once on the start screen, applied at scene build time (no live runtime reconfiguration needed for v1).

## Key Dependencies

`three`, `@dimforge/rapier3d-compat`, `vite`, `typescript` as core; `stats.js` and `lil-gui` for dev-time performance monitoring and live-tunable physics/combat/AI constants (gated out of production build); `three/examples/jsm` for GLTFLoader/EffectComposer. Added incrementally per phase, not all at bootstrap.

## Verification Approach

No automated test framework — verification is manual but structured: an always-available debug overlay (`DebugGizmos.ts`) visualizing raycasts, combat range/arc cones, AI waypoint targets, and ragdoll joints; `stats.js` for performance regressions; `lil-gui` for live physics/AI/combat tuning; a specific manual checklist per phase (see below); repeated-race stress testing for AI/combat since bot decisions involve randomness; console-assert invariant checks for state-machine bugs (e.g. ragdoll body count returns to zero after teardown); a final cross-browser (Chrome + Firefox) smoke test before considering v1 done.

## Future Cycles (explicitly out of scope now)

Manual transmission, health/damage system, multiple tracks/bikes/avatars, score/progress persistence, weapons/grabs/blocking, AI difficulty scaling, mobile/touch controls.

### Phase 1 — Drivable box
**Status:** Done — confirmed by user in browser after an extended debugging pass (see hiccups): box accelerates, brakes, steers the correct way, and stays upright under hard steering and sustained throttle
Placeholder box vehicle with raycast wheels, keyboard input, automatic drivetrain, fixed-offset camera.
*Verify:* box accelerates/brakes/steers correctly, cannot reverse past tolerance, feels roughly right on flat ground.
- Implementation notes:
  - **Vehicle physics uses Rapier's own built-in `DynamicRayCastVehicleController`** (`@dimforge/rapier3d-compat/control`) rather than a hand-rolled raycast-suspension loop as originally sketched in the plan. This was a deliberate upgrade found while implementing: it's a tested port of Bullet Physics' `btRaycastVehicle` already bundled with our physics engine, handling per-wheel suspension springs/damping, engine force, braking, and tire friction/slip natively — strictly less risk than reimplementing the same raycast math by hand, so it replaces §3's manual pseudocode while keeping the same wheel count (2, front+rear) and the same tunable concepts (stiffness, damping, friction).
  - `src/physics/VehicleController.ts` — wraps the Rapier vehicle controller: front wheel (index 0) is steered, rear wheel (index 1) is driven; `DEFAULT_VEHICLE_CONFIG` holds all tunable constants (engine force, brake force, steer angle/speed, suspension stiffness/damping, friction, reverse tolerance, estimated top speed).
    - Drivetrain: throttle maps to rear-wheel engine force through a speed-based torque curve (`1 - speedRatio²`) that tapers acceleration as the bike approaches its estimated top speed, giving a natural asymptotic feel without an explicit gear table.
    - Reverse: braking applies while still moving forward; only once stopped does a small reverse creep become available, itself capped at `reverseTolerance` (0.6 m/s default) — satisfies the "hard block past a small tolerance" requirement.
    - Steering: front-wheel angle eases toward the input target at a max angular rate (`steerSpeed`) rather than snapping instantly, and steering effectiveness is reduced at higher speed for stability, matching the plan's speed-scaled steering.
    - **Upright stability — final approach: locked rotational axes, not a corrective torque.** A 2-wheel centerline vehicle has no inherent roll or pitch stability (unlike a 4-wheel car). This was first implemented as a PD corrective torque pulling the chassis's up-vector toward world-up each tick; that approach was tried, tuned across four rounds, and ultimately **abandoned** (see hiccups) because a reactive spring can always be out-accelerated by a large enough disturbance torque, and stiffening it enough to win introduces oscillation instead. The shipped solution locks the chassis body's pitch (X) and roll (Z) rotational degrees of freedom outright via Rapier's `RigidBodyDesc.enabledRotations(false, true, false)`, leaving only yaw (Y) free for steering. The chassis is now *physically incapable* of tipping or wheelieing regardless of applied force — "the chassis never tips over from steering alone" (the plan's requirement) becomes a structural guarantee rather than a tuning outcome. The cosmetic lean-into-turns effect is unaffected, since the plan always specified it as render-mesh-only (Phase 3).
  - `src/entities/Bike.ts` — placeholder blue box body (with a yellow cone "nose" so forward direction is visible while driving) + two visible black cylinder wheels positioned/rotated each frame from the vehicle controller's live wheel-contact data; owns the previous/current transform snapshots used for render interpolation.
  - `src/entities/PlayerController.ts` — reads WASD/arrow-key state from `InputManager` each fixed step, maps to bike throttle (`W`/`↑` minus `S`/`↓`) and steer (`D`/`→` minus `A`/`←`) input.
  - `src/core/InputManager.ts` — generic keyboard state tracker (`isDown`, `isAnyDown`, `wasJustPressed`), deliberately not baking in a game-specific action schema so later systems (combat's P/K, menus) can query it without changes here.
  - `src/camera/ChaseCamera.ts` — Phase 1 fixed-offset third-person follow (no spring-damper smoothing or collision pullback yet — those are explicitly Phase 3 per the plan, once there's real scenery to collide against).
  - `src/core/Game.ts` rewritten: floor collider now has friction set explicitly (1.0); wires up `InputManager` → `PlayerController` → `Bike` → `VehicleController`; fixed-step loop now correctly splits into `bike.prePhysicsStep(dt)` (apply drive/steer/stabilization, snapshot previous transform) → `physics.step()` → `bike.postPhysicsStep()` (capture newly-integrated transform) each fixed tick, so render interpolation (`bike.syncRender(alpha)`) is smooth and uses genuinely correct prev/curr physics states.
  - Added a `lil-gui` debug panel (dev-build only, gated behind `import.meta.env.DEV`) exposing live sliders for drivetrain (engine force, brake force, top speed, reverse tolerance), steering (max angle, turn rate), suspension (stiffness, damping, friction, side-friction), and upright stabilization (stiffness, damping) — lets handling be tuned by feel without code edits/reloads, per the plan's verification approach.
  - `npx tsc -b` passes (strict mode), `npm run build` succeeds.
- Hiccups / errors encountered:
  - **Fixed-step ordering bug caught before testing**: initially captured the bike's "current" render transform immediately after calling the vehicle controller's per-tick update, but that call only *sets* the chassis's target velocity — the actual position/rotation isn't integrated until `physics.world.step()` runs afterward. Caught by re-reading the code against how Rapier's raycast vehicle controller is documented to work ("directly updates the velocity... "). Fixed by splitting `Bike`'s per-tick logic into `prePhysicsStep()` (pre-integration: set forces/velocity, snapshot previous transform) and `postPhysicsStep()` (post-integration: capture new transform), called on either side of `physics.step()` in `Game.ts`'s loop.
  - **Upstream typo in Rapier's TypeScript definitions**: `DynamicRayCastVehicleController`'s forward-axis setter is declared as `set setIndexForwardAxis(axis: number)` instead of `set indexForwardAxis(...)` (every other property in that class follows the normal `get x()/set x()` pairing — this one alone doesn't), so TypeScript sees `indexForwardAxis` as read-only. Worked around by assigning to the oddly-named `vehicle.setIndexForwardAxis = 2` property instead, with a comment explaining why, so it doesn't look like a future typo of ours.
  - **Stale compiled `.js` files silently shadowing the real `.ts` sources** — by far the biggest time sink of the phase. Symptom: the browser kept executing Phase 0's falling-box code no matter what was changed, across many ports, surviving hard refreshes *and* Incognito. Root cause: an earlier diagnostic command, `npx tsc -b --noEmit false`, overrode the project's `noEmit: true` and emitted `main.js`, `core/Clock.js`, `core/Game.js`, `render/SceneSetup.js`, `physics/PhysicsWorld.js` next to their `.ts` originals; Vite's default `resolve.extensions` tries `.js` **before** `.ts`, so every extensionless import (`import { Game } from "./core/Game"`) silently resolved to the stale compiled copy. Fixed by deleting all stray `.js`/`.js.map` files under `src/`, deleting `tsconfig.tsbuildinfo`, clearing `node_modules/.vite`, and restarting the dev server.
    - **Lessons recorded so this can't recur**: (1) never override `noEmit` via a CLI flag on this project — if a type-check is wanted, plain `npx tsc -b` already does it without emitting; (2) `find src -name "*.js"` is now run as a standing sanity check after anything `tsc`-related, and should return nothing; (3) the decisive diagnostic was the *user's own browser console* showing a log string (`"[Phase 0] Rapier physics world stepped successfully."`) that no longer existed anywhere in the source tree — proving the browser was running different code than the server returned when the same file was fetched directly. Diagnosing via "View Page Source of `index.html`" was a wasted step, since `index.html` was byte-identical between Phase 0 and Phase 1 and could never have revealed the difference.
  - **Suspension raycast too short to ever reach the ground** (symptom: bike sat dead on its belly and "vibrated" under throttle instead of moving). Each wheel's suspension ray only searches `suspensionRestLength + wheelRadius` downward *from its mount point*, but the wheels were mounted at the chassis's **center**, leaving a ~1.0-unit gap to the ground vs a 0.7-unit ray — so no wheel ever registered ground contact, the chassis rested on its own box collider, and the vehicle controller had zero traction to work with. Fixed by mounting wheels at the chassis's local **bottom** (`y = -halfExtents.y`), lowering `chassisHalfExtents.y` 0.5 → 0.3, and raising `suspensionRestLength` 0.35 → 0.45. (A `GridHelper` was also added to the ground here — unrelated to the bug, but on a featureless flat green plane there was no visual reference to tell motion from stillness in the first place.)
  - **Throttle drove the bike backwards.** Rapier's raycast vehicle controller measures `currentVehicleSpeed()` and applies `setWheelEngineForce()` along the *opposite* of the local +Z that had been chosen as "forward" for the chassis (the direction the nose marker points and the chase camera sits behind). Fixed with a single `FORWARD_SIGN = -1` constant applied at exactly two boundary points — a `forwardSpeed` getter and a `toRawEngineForce()` helper — rather than scattering sign flips; the rest of the class is written purely in "our" convention.
  - **A/D steered the wrong way** (A turned right, D turned left) — the *same* mirrored-axis mismatch as above, surfacing again on the steering channel once the bike was stable enough to corner properly. Fixed by negating only at the `setWheelSteering()` handoff, deliberately leaving `currentSteerAngle` in our convention so `Bike.ts`'s front-wheel mesh rotation stays correct.
  - **Wheelie-then-topple under throttle, and falling over on hard steering — four rounds to actually fix, and the first three were the wrong shape of fix.** Rounds 1–3 all treated it as a *tuning* problem (lower `maxEngineForce` 3400 → 1200; raise `uprightStiffness` 55 → 220 → 300; raise `uprightDamping` 6 → 24 → 30 → 280 after working out that critical damping for a torque spring is `c = 2·√(k·I)` and the values in use had been ~10x underdamped, making the "stabilizer" itself oscillate and pump up the very toppling it was meant to prevent). A genuine *structural* improvement did land in round 2 — `cancelDrivePitchTorque()`, which computed the exact nose-up torque the drive force would produce at the wheel's below-COM contact point (~700 N·m) and cancelled it in the same frame, equivalent to applying drive force at COM height — but it only addressed the torque the code applies *itself*, leaving cornering-friction and weight-transfer torques generated inside Rapier's own tire model still able to tip the bike. Round 4 dropped the reactive approach entirely in favour of locking the pitch/roll axes (see implementation notes), which cannot be out-accelerated by any disturbance and has no gains to oscillate. `cancelDrivePitchTorque()` and the whole PD stabilizer were then deleted as dead weight, along with their now-meaningless `uprightStiffness`/`uprightDamping` config fields and "Upright Stabilization" GUI folder.
    - **Lesson recorded**: when a stability problem survives two rounds of gain-tuning, that is the signal to change the *mechanism*, not the numbers. A reactive controller fighting a disturbance is inherently a losing race; removing the degree of freedom the disturbance acts on ends the race. This is worth remembering for Phase 5's ragdoll, which will have the opposite requirement (rotations must be free) and will therefore need genuinely different treatment rather than a copy of this fix.
- Deferred items: none — phase scope unchanged. (Full gear-index/RPM simulation and engine audio are already scoped to Phase 3 in the plan, not this phase — Phase 1's torque curve covers acceleration *feel* only, no sound yet.) Note that locking pitch/roll is correct for a *riding* chassis but must be **released** when the rider is knocked off in Phase 5 — the bike needs to tumble freely then. Flagged here so it isn't forgotten: `enabledRotations` is set once at body creation in `VehicleController`'s constructor and will need a runtime `setEnabledRotations(true, true, true, true)` call on the knockdown transition.

### Phase 2 — Real track
**Status:** Done — confirmed by user driving the course
Spline-based road/off-road/collision, hills, finish trigger.
*Verify:* can drive the full point-to-point layout, off-road feel is distinctly different from on-road, finish trigger fires exactly once per rider crossing.
- Implementation notes:
  - `src/track/TrackDefinition.ts` — the course itself: 82 control points through a `CatmullRomCurve3` (centripetal, tension 0.5), producing a **2495 m** point-to-point route. The layout is authored as a sequence of straights and constant-radius corners so it has a genuine brake-turn-accelerate rhythm: 11 corners, of which **6 are tight enough to force braking** from the ~144 km/h top speed down to 84–88 km/h, the rest fast sweepers taken flat out (see the corner-rhythm rework in hiccups below). `arcLengthDivisions` is raised to 4000 (the default 200 is far too coarse over ~2 km) so arc-length parameterisation is accurate and evenly-spaced samples really are evenly spaced. Precomputes ~833 centerline samples at ~3 m spacing, each with point, forward tangent, and right-vector (`right = up × forward`, the right-handed basis convention used consistently across the codebase).
    - `project(position, hintIndex)` answers "where is this rider on the track" — returns distance along, signed lateral offset from centre, nearest centerline point, and tangent. This is the shared primitive that on/off-road logic, the HUD, finish progress, fall-recovery, and (later) AI waypoints and wrong-way detection all build on, so it was worth building properly now rather than per-consumer.
    - Performance: passing the previous frame's `sampleIndex` back as `hintIndex` narrows the search to a ±40-sample window, turning an O(833) scan into a fixed small one per rider per step — which matters once there are 6 riders at 60 Hz. Correctness guard: if the best match lands on the window's edge, it falls back to a full scan, so a respawn or teleport can't leave a rider permanently locked onto the wrong stretch of track.
  - `src/physics/TerrainMaterial.ts` — `SurfaceProperties` (grip + rolling resistance) with `ROAD_SURFACE` / `OFFROAD_SURFACE`, and a `SurfaceRegistry` mapping collider handles to surfaces. Unregistered colliders deliberately fall back to road, so a collider someone forgets to register can never silently make a rider undriveable.
  - `src/track/TrackBuilder.ts` — generates the geometry from the spline. A single `buildBand()` helper sweeps a ribbon between two lateral offsets along the whole course and is reused for every strip: road surface, the two off-road bands, both edge lines, and the dashed centre line (via a `segmentFilter` that emits 2 of every 5 segments ≈ 6 m dash / 9 m gap). Each band produces both the Three.js `BufferGeometry` and the `Float32Array`/`Uint32Array` pair for a matching Rapier trimesh collider, so render and collision geometry are generated from one source and cannot drift apart.
    - Road is 14 m wide, off-road extends to 30 m each side, and the off-road outer edge drops 2.5 m so terrain reads as falling away rather than as a flat carpet.
    - Road and off-road are **separate colliders on purpose** — that separation is exactly what lets the vehicle identify what it's riding on at runtime.
    - Finish line: a red painted band, a posts-and-banner gantry visible from a distance, and a sensor cuboid spanning the road width (6 m tall, so a rider who catches air still trips it), placed 50 m before the spline's end to leave run-out room. Blue band marks the start.
  - **Surface-aware grip** (`VehicleController.applySurfaceGrip`): each tick, every wheel reports which collider it's resting on via Rapier's `wheelGroundObject(i)`; that's looked up in the `SurfaceRegistry` and the wheel's friction is set from the result. Off-road applies *both* penalties the design calls for — grip drops from 3.2 to 1.15, and a speed-proportional drag force (70 N per m/s) is applied to the chassis, sized so the drag curve meets the engine's falling torque curve at roughly 20 m/s instead of the ~40 m/s the road allows. So going off-road costs both cornering ability and top speed, roughly halving the latter.
    - The old fixed `frictionSlip` config field was replaced by a `gripMultiplier` that *scales* whatever the current surface provides. This keeps live GUI tuning available without flattening the road/off-road difference, which a single absolute grip slider would have done.
  - **Render-only terrain pitch** (`Bike.updateVisualPitch`): a direct consequence of Phase 1 locking the chassis's pitch axis — on a hill the physics body stays level while the road slopes under it. The visible bike is pitched to match the real slope, measured from the two wheels' actual contact points (`wheelContactPoint`), smoothed with a frame-rate-independent exponential blend, and decaying back to level while airborne. This is the same "cosmetic transform on the mesh, never on the physics chassis" approach the plan already specifies for lean-into-turns, so Phase 3's lean will layer onto it cleanly. Wheel meshes are deliberately positioned from the *unpitched* physics orientation, since their hard points come from the physics chassis and pitching them too would slide them out of their suspension travel.
  - `src/render/SceneSetup.ts` — the flat 200×200 ground plane and the temporary Phase 1 `GridHelper` are both gone, replaced by real track geometry. Fog and camera far-plane pushed out for the larger world. - Hiccups / errors encountered:
  - **Locking the chassis's pitch axis in Phase 1 turned out to constrain the track design**, which wasn't obvious when that fix was made. A level chassis on a sloped road forces the suspension to absorb the height difference across the 1.4 m wheelbase; at ~10% grade that's about 0.14 m against 0.25 m of available travel, so grades meaningfully steeper than that would bottom out the suspension and let the chassis clip the road. Worth recording as a genuine trade-off of the Phase 1 stability fix rather than a free win.
  - **Controls did nothing at all** after the track landed — no throttle, no steering, arrows and WASD both dead. Rather than guess, the failure was made observable first: `src/core/ErrorOverlay.ts` (a full-screen red panel for uncaught errors) plus a `try`/`catch` around the RAF loop, and three diagnostic HUD lines reporting raw input values, per-wheel ground contact, and applied engine force. Root cause: the bike spawned at track distance 0, which is exactly where the road ribbon begins, and the rear wheel sits ~0.7 m *behind* the chassis centre — i.e. over nothing. The rear wheel is the driven one, so every newton went into a wheel spinning in mid-air. Needed for Phase 4's staggered 6-rider grid regardless.

A silent RAF-loop death is indistinguishable from "the controls stopped working", which is exactly how this was first reported.
  - **The left off-road band was wound backwards** (found by code review, not by symptom). `buildBand` computes winding from the inner → outer lateral ordering, but for the left band `innerLateral = -7` and `outerLateral = -30`, so outer < inner, reversing the cross product and pointing every normal downward — it would have rendered as an unlit black strip beside the road. Fixed with an explicit `reversed` flag selecting the index order.
  - **Steering got *twitchier* with speed, the exact opposite of what it should do.** The original model shrank the maximum steering angle as speed rose (32° → ~11°), which looks like the right idea but isn't: yaw rate is `v·tan(δ)/L`, so it *grows* with speed, and shrinking the angle by 3× while speed rises 8× still leaves the bike turning far faster at speed — about 350°/s at 90 km/h against 67°/s at 10 km/h. Reworked to cap **lateral acceleration** (`maxLateralAccel`, 11 m/s² ≈ 1.1 g) instead of angle: the available angle then falls off as 1/v², achievable yaw rate becomes `a/v` and genuinely *decreases* with speed, and corner radius `R = v²/a` widens naturally. A separate speed-dependent bar rate (`steerSpeed` → `steerSpeedAtTopSpeed`, 220°/s → 70°/s) makes fast steering feel heavy; straightening is deliberately exempt from that slowdown so recovering a bad line stays responsive. A `steering  X° of Y° available` HUD line exposes the shrinking limit live.
  - **The track was too easy to make any of that steering work perceptible.** Adding the corner check immediately revealed the layout's real problem: the tightest corner was 187 m radius, holdable at 163 km/h against a ~144 km/h top speed, so **every corner could be taken flat out** and the course had no braking points at all. The 21 original control points were ~100 m apart with gentle direction changes, which can only produce fast sweepers. Rebuilt the layout (with the user's go-ahead) as an explicit sequence of straights and constant-radius arcs, generated by a scratch tool that emits control points along the intended route and then *measures what the resulting spline actually does*. Two things came out of that which weren't obvious up front:
    - **The off-road band width sets the minimum corner radius, not grip.** The band extends `OFFROAD_HALF_WIDTH` (30 m) from the centerline, so inside a corner tighter than 30 m its outer edge passes through the centre of curvature and the ribbon turns inside out. With margin that puts the floor at ~39 m radius ≈ 76 km/h, which is what actually caps how slow the slowest corner can be. Narrowing the off-road would buy hairpins; left at 30 m for now since that's a change to how the world looks.
    - **Uneven control-point spacing pinches corners up to 25% tighter than drawn.** A 90 m gap on a straight butting against a 15 m gap in a corner makes the Catmull-Rom overshoot at the junction — corners specified at 45 m radius came out at 32 m. Fixed by driving spacing from the route's local curvature *min-filtered over a ±45 m window*, so spacing tightens on approach to a corner as well as inside it. Points now run 16–56 m apart and the spline tracks its intended radii closely.
    - **Correction recorded**: the target radii were initially quoted as 50–90 m for 60–80 km/h corners. That was wrong — `v = √(a·R)` puts 50–90 m at 84–113 km/h. The braking corners are 49–54 m, holdable at 84–88 km/h.

- Implementation notes:
  - `src/physics/Transmission.ts` — simulated 6-speed automatic gearbox and tachometer. Feeds **audio and the HUD only**; drive force still comes from `VehicleController`'s continuous torque curve, exactly as the design specifies ("RPM/gear simulated internally for engine sound/feel only"). Ratios are expressed as *the road speed at which each gear hits the redline* (`[8, 14, 20, 27, 33, 40]` m/s) rather than as gear/final-drive numbers, which makes the one property that matters — where shifts land relative to the ~40 m/s top speed — directly readable and directly tunable. A 0.35 s shift cooldown stops the box hunting at a ratio boundary, since crossing a shift point immediately moves the rpm toward the *other* threshold. The gear index is kept as real state rather than derived on the fly, so a future manual-transmission mode has something to shift.
  - **Cornering lean** (`Bike.updateVisualLean` / `applyLean`) — render-only, like the terrain pitch, since the physics chassis's roll axis is locked and must stay that way. Two decisions worth recording:
    - **The angle comes from real cornering acceleration, not from steering input.** `VehicleController.lateralAcceleration` returns `speed × yawRate` read from the chassis's actual angular velocity, and the lean is `atan(a / g)` — the exact angle at which gravity and cornering force line up through the contact patch on a real motorcycle. This makes the lean *informative*: how far the bike is laid over tells you how close you are to the limit, which at the 11 m/s² cap works out to ~48°. Deriving it from commanded steering instead would have the bike leaning into turns it isn't actually making whenever grip runs out — visibly wrong the moment you put a wheel off-road.
    - **The bike rolls about the line through its tyre contact patches**, not about the chassis centre. Rolling about the centre is a one-liner, but the contact patches would swing sideways by `wheelHeight × sin(lean)` — about a third of a metre at full lean — so the tyres would skate out from under the bike and visibly hang off the road on a hard corner. The pivot is the average of the two wheel-bottom points, and body and both wheels are rotated about it together.
  - `src/camera/ChaseCamera.ts` — rewritten from the Phase 1 fixed offset into a real spring arm. Four mechanisms, each doing a distinct job: (1) **critically damped smoothing** of both camera position and aim point (the standard `SmoothDamp` formulation — second-order with a velocity term, because the slight lag-then-settle is what reads as weight; a first-order lerp just feels mushy, and the rational `exp` approximation keeps it stable when a frame is dropped); (2) **speed pullback** on distance, height and field of view (60° → 78°), the FOV doing most of the work since widening the frame is the strongest speed cue available before post-processing; (3) **collision pullback** by raycast, scaling distance and height together so the camera slides along the arm it was already on rather than dropping to bike height; (4) **roll** at 35% of the bike's lean, applied through `camera.up` *before* `lookAt` so there's no order-of-operations trap. The arm is built from the physics (yaw-only) orientation, never the leaned/pitched visual transform — hanging it off the visual transform would swing the whole world every time the bike tips into a corner.
    - The collision ray excludes sensors deliberately: the finish-line trigger spans the full road width and is 6 m tall, so without that flag it would yank the camera into the rider's back at the moment they cross the line.
  - `src/audio/EngineAudio.ts` — **synthesised**, not sampled, so it needs nothing sourced or bundled and can't drift out of sync with the physics. Engine is three detuned oscillators (saw at 1×, square at 2.01×, saw at 0.5×) through a low-pass whose cutoff opens with **both rpm and throttle** — that load-dependent timbre change is what separates "engine" from "sine wave", and does more for believability than stacking more oscillators. Frequency tracks the transmission, so upshifts audibly drop the note. Wind is a 2 s looped white-noise buffer through a low-pass that opens with speed, mixed as speed², which also usefully masks the synthetic edge of the oscillators at high speed. All parameter changes go through `setTargetAtTime` to avoid zipper noise.
    - Browsers refuse to start an `AudioContext` without a user gesture, so the graph is built at load and stays silent until the first keydown/pointerdown resumes it. The whole class no-ops safely if Web Audio is missing, and the HUD shows `(audio: press a key)` until it's actually running.
  - `src/core/Game.ts` — wires the audio, passes frame delta to the camera, adds `gear`/`rpm` to the HUD readout, and adds "Chase Camera" and "Audio" folders to the dev GUI (follow distance, speed pullback, follow lag, FOV at speed, roll fraction; volume and mute).

  - **The splitter keys off a whole mesh's signature, not a height slab.** A wheel mesh has a shape nothing else on a bike has: its triangles fall into two well-separated groups along the wheelbase, each as tall as it is long, both the same size, sitting on the ground. Radius comes from the lobe height, the hubs from the lobe centres.
  - **Two tests, both required.** A mesh is split off only if ≥95% of it lies inside one of the two wheel discs **and** its triangles wrap the hub — spread across at least 75% of 16 angular sectors, as any solid of revolution is. The second test is the one that matters: being inside the disc says nothing about whether a part turns. On this model that selects `Object_8` (hubs), `Object_19` (rims) and `Object_24` (tyres) — 3,308 triangles — and rejects `Object_2` and `Object_4`, which sit inside the discs but cover 3–4 sectors out of 16.

  - `scripts/run-sim.mjs` bundles the TypeScript with esbuild before running it, because the sims import from `src/` with extensionless specifiers that Node's ESM resolver can't follow. The bundle is written inside `node_modules` rather than the OS temp dir — it keeps `three` and Rapier external, and Node resolves those by walking up from the bundle's own location, which from `/tmp` finds nothing.
  - Sibling probes, each of which exists because a specific question came up and guessing at it wasted time: `sim:probe` (which world axis is the bike's right), `sim:brake` (deceleration vs. `brakeForce`), `sim:skidpad` (cornering acceleration actually achieved vs. commanded), `sim:corner` (traces one bot through one stretch of track, printing why it does what it does).
- Implementation notes:
  - `src/entities/Racer.ts` — one rider: a bike, whoever is driving it, and cached track position. The `Driver` interface (`tick(dt)`) is implemented by both `PlayerController` and `OpponentAI`, so the game loop drives all six riders through one code path — the design's "no divergent AI-vs-player code" requirement, established now rather than retrofitted at the combat phase. Also holds finish state and the stuck-detection timer.
  - `src/ai/RiderPersonality.ts` — five named opponents varying in cornering confidence, top-speed fraction, preferred line across the road, steering trim and reaction time. The point is *variance, not difficulty*: five bots on one optimal line finish nose-to-tail in the same order every race, which reads as scripted. `aggression` is declared but unused, so bot identity lives in one place when combat arrives.
  - `src/ai/OpponentAI.ts` — **pure-pursuit steering** plus corner-limited speed. The bots use no privileged information and no forces the player lacks; a bot is quicker because it picks a better line and brakes at the right moment, not because it cheats.
  - `src/ai/AvoidanceBehavior.ts` — sideways bias away from nearby riders, deliberately expressed as a *bias on the desired line* rather than a steering override, so avoidance and cornering blend instead of fighting for the bars. Ties (two riders exactly abreast) break toward the side of the road the rider already prefers, because defaulting the sign sent every bot the same way and caused the pile-up it was meant to prevent.
  - `TrackDefinition` gained runtime curvature: `sampleRadii`, `cornerRadiusAt()` and `speedLimitAhead()`. The last is what produces a braking point — for each point ahead it asks "how fast may I be *here* and still shed enough by *there*" (`v = sqrt(v_corner^2 + 2*decel*gap)`) and takes the tightest answer, so the limit sits at top speed until a corner comes within braking distance and then falls smoothly. It mirrors what `check-track.mjs` measures offline.
  - `src/core/Game.ts` — rebuilt around a field of six. Staggered 2-abreast grid (which is what `START_LEAD_IN` was added for back in Phase 2), one shared finish sensor resolved through a collider-handle → rider map, live standings, and per-rider rescue. The player starts last, so the race opens with the whole field visibly ahead.
  - **Autopilot (`O`)** hands the player's bike to an AI driver. Added specifically because this phase's verification says "run a race with only AI", which is otherwise impossible to watch from inside a game that always has a human in it.
  - `BrakeToStopDriver` takes over a rider's bike the moment they cross the line. Without it a finished rider carries on at 130 km/h and runs off the end of the spline 1.4 s later, which the recovery system then rescues in a loop.
- Hiccups / errors encountered:
  - **`forwardSpeed` had been returning the wrong sign since Phase 1 — negative while riding forwards.** The headless sim exposed it immediately: the trace showed −119 km/h while the distance-along column climbed steadily. Confirmed against ground truth (chassis linear velocity dotted with the nose direction) with `sim:probe`. Phase 1 correctly established that Rapier applies *engine force* along the opposite of our forward axis, and then over-generalised: `currentVehicleSpeed()` is **not** mirrored. That one sign silently disabled three separate things at once, none of which announced itself:
    - **The brakes did nothing above walking pace.** `if (forwardSpeed > 0.05)` could never be true while moving, so `S` applied no braking force at all — the bike only ever coasted down on damping.
    - **The engine's top-speed taper never engaged.** `clamp(negative / topSpeed, 0, 1)` pinned the torque curve at full output forever, so `topSpeedEstimate` had no effect on anything and the bike just accelerated until drag caught it.
    - **The AI could not slow for corners**, because its speed error was computed against a negative number and always demanded full throttle.
    - Renamed the constant to `ENGINE_FORCE_SIGN` and applied it only at the force handoff. **Lesson**: the tell was there all along — every consumer wrapped this getter in `Math.abs()`, which is what you write when a value's sign is inconvenient, and is worth treating as a symptom rather than a fix.
  - **Which axis is the bike's right, settled properly.** The Phase 3 lean fix reasoned that a right turn implies a negative yaw rate, and concluded the bike's right is −X. That conclusion was right, but the reasoning used the broken `forwardSpeed` and so was accidentally correct. Re-established by measurement: `sim:probe` drives with `steerInput = +1` (which the user confirmed in the browser turns right) and reports −40 m of displacement along +X over five seconds with a negative yaw rate throughout. `src/utils/Directions.ts` now states both facts, cites the probe, and says to re-run it rather than re-derive.
  - **`linearDamping: 0.3` was the real top-speed limit, not the torque curve.** Once the taper started working, every rider capped out at exactly 86 km/h. The damper costs `0.3 × 220 × v` = 66·v newtons and balances a 2200 N engine at 23 m/s. Top speed should come from the engine tapering to zero at `topSpeedEstimate`, so damping dropped to 0.05 and riders now reach ~131 km/h. (Surface drag remains separate and per-surface in `applySurfaceGrip`.)
  - **`brakeForce` is not newtons.** Rapier treats it as a brake impulse and it bites far harder than the name suggests: `sim:brake` measured the shipped value of 60 as **33 m/s², about 3.4 g**, stopping the bike as if it hit a wall. Nobody noticed because the sign bug meant the brakes had never once been applied. Now 20, measured at 12.1 m/s² (~1.24 g).
  - **The road turned invisible.** Reported by the user: "the roads are all gone". Correcting the meaning of "right" in `utils/Directions` mirrored every band's vertices about the centreline, which inverted all the triangle winding — so every surface's normals pointed downward and rendered backface-culled and unlit, while remaining perfectly solid to the physics. The headless race sim had passed on that build, because riders were still driving on a track the player could not see.
    - Root cause was a `reversed` flag that inferred winding from `outerLateral < innerLateral` — a guess about geometry made from *parameters*. The lateral numbers never changed; the vertices moved. Replaced with `ensureUpwardWinding()`, which measures the largest built triangle's actual normal and flips the index order if it faces down (largest, not first, because a dashed band's leading triangle can be a sliver whose normal is numerical noise). It cannot be wrong about geometry it inspected.
    - `scripts/race-sim.ts` now asserts every swept band's mean normal points up before racing. Band meshes are tagged `userData.isTrackBand` so the check can tell them from the line markers and gantry, whose box normals correctly average to zero — the first version of the check flagged all five boxes and no actual bands.
    - **Lesson**: a headless simulation validates behaviour, not appearance. It passed a completely invisible track. Any check that runs without a renderer needs at least one assertion about what the thing *looks* like, or it certifies the wrong half of the program.
  - **Proportional steering gain cannot work on this vehicle, at any value.** The first AI steered with a P gain on the angle to its aim point, and understeered off the outside of every fast corner. The reason is structural: steering lock is capped by cornering acceleration and so falls as 1/v², leaving about **0.7° of total lock at 130 km/h**, while a 185 m sweeper needs ~70% of that and presents an aim angle of only ~5°. A gain that feels right at 60 km/h commands a fifth of what's needed at 130. Replaced with **pure pursuit**, which computes the required steering angle from the geometry (`curvature = 2·sin(α)/d`, `angle = atan(wheelbase · curvature)`) and divides by the lock currently available — no gain to mistune, self-adjusting across the speed range. `steerGain` became `steerTrim`, a stylistic multiplier near 1.0.
    - Before rewriting it, `sim:skidpad` was used to rule out the alternative explanation: the bike delivers **9.9 m/s²** of cornering against 11 commanded, consistently at every speed, so grip was fine and the fault really was the controller. Bot `corneringConfidence` values were then all moved below 9.9 — a bot planning corner speeds it cannot hold simply understeers off.
  - **Cornering was too tight to be fun, and lifting off did nothing.** Reported by the user driving it: at speed the bike could only be turned by braking, never by simply releasing the throttle. Two independent causes, both measured before either was touched:
    - `maxLateralAccel` was 11 m/s^2 (~1.1g), a realistic *road* motorcycle figure. Minimum radius is `v^2 / a`, so at 131 km/h that is a 134 m arc — and the track's fastest sweepers are 140-192 m. Every fast corner therefore had to be taken at the absolute limit with no margin, and braking was the only thing that could make one. Realistic, and not the game this is meant to be; the design says "arcade-sim hybrid" and Road Rash was arcade. Raised to 16 (delivering ~14.4, ~1.45g, roughly MotoGP), which gives a 92 m minimum radius at top speed: the five sweepers are now flat out and only the six tight corners need braking.
    - **Grip was never the constraint.** Before changing anything, `sim:skidpad` was rebuilt to sweep `gripMultiplier` against commanded cornering, and the answer was flat: achieved cornering tracks the commanded cap at exactly 90% at every grip value from 1.0 to 2.5. The tyres never let go, so `maxLateralAccel` alone governs and no grip retuning was needed. Worth having checked — "add more grip" was the obvious fix and would have done nothing.
    - Added `engineBrakeForce` (4, measured at ~3.5 m/s^2 of lift-off deceleration over 138 m). Linear damping alone gave only ~1.8 m/s^2 at speed, which is why releasing the throttle felt inert. Faded out below 2 m/s so it can't fight the reverse creep.
    - Bot `corneringConfidence` values were all rescaled from the 9.9 the bike used to deliver to the 14.4 it delivers now, keeping the same spread of daring — they plan corner speeds from this number, and a bot planning speeds it cannot hold understeers off. Race sim after the change: 78.0 s (down from 84.0), 0 rescues, 2.3 s spread.
    - `check-track.mjs` now computes holdable speeds from the *delivered* 90%, not the commanded cap, so it agrees with the road instead of carrying a footnote saying it doesn't.
- Deferred items:
  - **No randomness in bot decisions yet**, so repeated races are identical. The plan calls for repeated-race stress testing precisely because AI decisions involve randomness — that arrives with the combat phase, and the stress testing belongs with it.
  - **`scripts/` is not type-checked.** `tsconfig.json` includes only `src`, and adding `scripts` would need `@types/node`, which isn't a dependency. The sims are checked by running, not by `tsc`.
  - **No overtaking-specific behaviour** — bots avoid each other and vary in pace, which produces position changes, but there's no explicit "attempt a pass" decision. Worth revisiting only after combat exists, since in Road Rash a pass and an attack are the same manoeuvre.

### Phase 5 — Ragdoll + recovery state machine
**Status:** In Progress — verified automatically and passing; pending user test in browser (X / Z)
Debug-triggered falls (before combat exists) to validate tumble/settle/getup/run/remount for player and AI.
*Verify:* falls at different speeds visibly tumble farther/differently; ragdoll doesn't explode/jitter; getup-then-run-then-remount sequence completes reliably.
- **Verification is automated.** `npm run sim:falls` knocks a rider off at 30/60/90/120/131 km/h and applies this phase's criteria as pass/fail: every recovery must complete, tumble distance must scale with speed by more than 2x, and the ragdoll body count must return to zero. `npm run sim:race` additionally throws one rider off mid-race at t=20 s and requires them to still finish, so the cycle is exercised inside a real race and not only in isolation. **Current result: PASS.**
  - Tumble 9.8 m at 30 km/h rising to 44.4 m at 131 km/h (4.5x); settle 3.9–6.0 s; total recovery 7.3–11.9 s; 7 bodies peak, 0 after teardown in every run. In-race: knocked off at 96 km/h, the victim recovered and finished, dropping P4 to P6 for a ~10 s penalty — punishing but not race-ending, which is about right for Road Rash.
- Implementation notes:
  - `src/physics/RagdollController.ts` — 7 bodies, 6 spherical joints (pelvis, torso, head, two arms, two legs). The plan allowed 6–9; limbs are one segment each rather than upper/lower pairs, because every extra joint is another constraint for the solver to fight over, at rider scale an elbow reads as noise, and fewer heavier bodies settle far more reliably. Settling reliably is the actual requirement — the state machine cannot advance until the ragdoll goes quiet.
  - **Nothing about the tumble is scripted.** The bodies inherit the bike's velocity at the moment of separation plus the knockback impulse, so distance and direction emerge from real momentum, which is what makes a 131 km/h fall throw you four and a half times further than a 30 km/h one.
  - `src/entities/RiderStateMachine.ts` — `RIDING → RAGDOLL → GETTING_UP → RUNNING_TO_BIKE → MOUNTING → RIDING`, identical for player and AI; `Racer.tickDriver` simply refuses to pass controls to a driver whose rider isn't on the bike. The plan's separate `FALLING` state collapsed into `RAGDOLL`: with a physics-driven fall there is nothing for it to *do*, since the bodies tumble from the moment they spawn and the exit condition is a settle test rather than an animation ending.
    - The runner is a single upright capsule with locked rotations, moved by setting horizontal velocity directly rather than by pushing with forces — running isn't a physics problem worth solving, and a velocity target can't build momentum and sail past the bike.
    - A 20 s run timeout force-mounts wherever the bike is. The race cannot proceed with a rider permanently on foot, and a bike that ends up somewhere unreachable must not strand them.
  - `VehicleController.setRiderAttached()` — **the `enabledRotations` release flagged as required back in Phase 1.** Detaching frees pitch and roll so a riderless bike tumbles; re-attaching re-locks them *and stands the bike upright*, because the locks only prevent new rotation, so a bike that came to rest upside-down would otherwise stay upside-down for ever.
  - `src/physics/CollisionGroups.ts` — explicit terrain/bike/rider layers. Also filters the suspension raycasts to terrain only, so a bike drives past a fallen rider instead of riding up over them.
- Hiccups / errors encountered:
  - **The ragdoll exploded instead of tumbling — twice, for two different reasons, and the same symptom hid both.** The tell was the settle time: every single run came back at exactly 6.0 s, which was the force-settle timeout, meaning the velocity test never once fired. Adding a peak-velocity readout turned a vague "it doesn't settle" into two specific numbers.
    - **First: riders collided with their own bike.** The ragdoll spawns at the seat and its legs reach down through the space the chassis collider occupies, so Rapier saw the overlap on the first step and resolved it with an enormous separation impulse — 26 m/s and 54 rad/s one second after a 60 km/h fall. Moving the spawn point clear would only have postponed it, since the bike is travelling at the same speed as the rider it just threw. Fixed with collision layers.
    - **Second: the ragdoll collided with itself.** Adjacent bones deliberately overlap — the head sits inside the top of the torso, the legs inside the pelvis — so the joints have somewhere to pivot without gaps opening at the seams. With self-collision on, every jointed pair is a permanent interpenetration that the solver pushes apart while the joint holds it together: 90–230 rad/s sustained for six seconds, limbs spinning thirty times a second. Excluding riders from their own layer is standard ragdoll practice, and costs only that two fallen riders pass through each other.
  - **The knockdown impulse was a cannon shell.** 900 N·s applied to a 26 kg torso is a 35 m/s kick — riders were fired 200 m down the road and the fall said nothing about how fast the bike had been going, which defeats the entire point of a momentum-driven tumble. Now 250 (about 10 m/s at the point of impact), so the rider's own speed dominates.
  - **A riderless bike at 131 km/h was still travelling two kilometres later.** Wheel brakes were applied, but a bike with its rotation locks released flips immediately, and once on its side the suspension raycasts point at the sky, find no ground and brake nothing. Fixed by raising the chassis's *linear and angular damping* while riderless, which doesn't care which way up the bike is — it now stops within about 35 m, close enough for a rider jogging at 5 m/s to reach.
- Deferred items:
  - **High-speed falls still reach the 6 s force-settle timeout** rather than passing the velocity test, though by then the tumble has finished (44.4 m at 131 km/h against 41.7 m at 120). Harmless, and the timeout is a deliberate safety net, but it means the settle threshold is still slightly optimistic at the top end.
  - **No skinned mesh** — the ragdoll renders as capsules. The plan calls for driving a rigged mesh's bones from the body transforms, which needs the Phase 3 asset pass; the body transforms it would read already exist, so that is a rendering change, not a physics one.
  - **Falls are debug-triggered only** (X for yourself, Z for the nearest rival). Combat supplies the real trigger in the next phase, and `knockOff(impulse)` is already the interface it will call.

### Phase 6 — Combat system
**Status:** In Progress — verified automatically and passing; pending user test in browser (P / K)
Hit detection/knockback wired to P/K and the Phase-5 fall transition.
*Verify:* hits land within the intended range/arc, knockback feels proportional to relative speed, cooldown prevents spam, whiffed attacks do nothing.
- **Verification is automated, and maps one-to-one onto this phase's criteria.** `npm run sim:combat` puts two riders on a flat plate at a chosen separation and bearing — no track, so geometry is the only variable — and checks all four: hits land inside the stated range and arc and nowhere else (tested either side of both boundaries, for both attacks); a whiff has no effect at all; exactly 1 of 56 requests during one attack is accepted, so cooldown genuinely prevents spam; and knockback rises with closing speed (240 → 264 → 288 at 0/5/10 m/s). It also confirms a landed hit puts the victim on the ground and leaves the attacker riding. **Current result: PASS.**
- Implementation notes:
  - `src/combat/AttackDefinitions.ts` — the punch and the kick as *data*: reach, arc half-angle, wind-up/active/recovery timing, knockback, and a closing-speed bonus. The combat code never learns which attack is which, which matters because next phase the AI picks between them and should be picking on numbers, not on a branch. The trade is the classic one and has to be legible at speed: punch 2.3 m / 0.1 s wind-up / 240 impulse; kick 3.0 m / 0.2 s / 420. A missed kick leaves you flailing for 0.6 s, and that cost is what makes throwing one a decision.
  - `src/combat/CombatSystem.ts` — one hit-detection and knockback path, shared. `PlayerController` calls `request()` from P and K; the AI will call the identical method. There is deliberately no "AI attacks player" code that could drift, and a bot has no reach, timing or force the player lacks.
    - **Strikes are measured from the attacker's sideways axis**, not their forward one, so a rider directly ahead or behind is out of reach however close they are. You swing sideways, as in the original.
    - One hit per attack, at the nearest valid target, however many physics steps the active window spans — the `hasConnected` latch, the same exactly-once shape as the finish sensor.
    - Knockback goes straight into `RiderStateMachine.knockOff` from the previous phase, so the tumble is the victim's own momentum plus the impulse and nothing about it is scripted here. The closing-speed bonus is deliberately small (2–3% per m/s): the ragdoll already inherits the victim's velocity, so a hit at speed throws them a long way unaided; this is the extra bite of being caught while converging, not the main effect.
    - Being knocked off cancels an attack in progress — you no longer have a bike to swing from.
  - `Bike.setStrike()` — placeholder fist, parented to the bike's render group so it inherits lean and terrain pitch for free; a punch thrown mid-corner swings from the leaned-over bike rather than floating upright beside it. It extends through wind-up and the live window and retracts through recovery, so what you see matches when the strike can actually land. Becomes a real arm animation with the rigged rider.
  - `EngineAudio.playImpact()` — short filtered-noise burst with a fast decay, pitched lower for heavier hits. Built per call and left to collect; hits are rare enough that pooling would be premature.
- Hiccups / errors encountered:
  - **Two bad closing-speed tests before a good one**, both testing the harness rather than the code. First attempt gave the victim a *forward* velocity, so they simply drove out of range during the 0.2 s wind-up and nothing connected. Second offset the pair by 40 degrees so the line between them had a forward component — but the faster attacker pulled ahead during the wind-up, rotating that line rearward until the relative velocity pointed *away* along it, and the measured impulse fell back to baseline. That read exactly like a scaling bug in `CombatSystem`. The fix was to have the victim close head-on along the line between them, so the bearing stays fixed while the gap shrinks.
    - **Lesson**: when a measurement disagrees with the code, suspect the measurement's geometry first if the quantity is defined relative to a frame that the test itself is moving.
  - A `THREE.MathUtils_clampish` shim briefly appeared in `EngineAudio` to avoid importing three.js for a single clamp. Replaced with a plain local function — inventing a fake namespace to dodge an import is worse than either the import or the four-line helper.
- Deferred items:
  - **No blocking, grabbing or weapons** — named as out of scope for this cycle in the plan, and still are.
  - **Attacks auto-target the nearest rider in the cone** rather than being aimed left or right. The confirmed control scheme is a single key per attack, so there is no input to aim with; if directional attacks are wanted later the definitions already carry a side.
  - **AI never attacks yet.** `CombatSystem.request()` is the interface it will use, and `RiderPersonality.aggression` has been sitting unused since Phase 4 waiting for it. That is the whole of the next phase.

### Phase 7 — AI combat behavior

Opportunistic engagement scoring wired into AI. Built on request with one addition: **an on-screen setting, "Bots attack you", off by default.** Out of the box the pack fights among itself and never touches the human; the switch (bottom-right, or `?botsAttack=1`) opts you in, mid-race if you like.

- **Verification is automated and maps onto the criteria.** `npm run sim:aicombat` (seeded, `SEED=n` to vary) runs three things: (1) a flat-plate check that an aggression-1.0 bot held beside the player never swings with the setting off and hits within a second or two with it on — the deterministic proof of the switch; (2) a full six-rider race with the default setting: every rider finishes, nobody ends off their bike, no ragdoll bodies leak, zero chases at and zero hits on the player, and the pack lands *some* hits but fewer than 8 per minute (measured 1.3–2.9/min, 2–6 per race, nobody knocked off more than twice); (3) two races with the setting on, requiring at least one chase at and one hit on the player between them (measured 4–10 chases, 2–3 hits). - Implementation notes:
  - `src/ai/CombatBehavior.ts` — the whole of the phase. A bot is a racer first; every 0.25 s it looks for a rider within ±9 m along the road, and rolls `aggression × 0.3` to go for the nearest. That opens an **engagement**: the bot's racing line is bent to 1.7 m beside the target (inside the punch's 2.3 m), its speed is matched to theirs with a gap correction (capped at ±4 m/s so it never brakes 40 km/h to "wait" for someone), and avoidance is suppressed against that one rider (`computeAvoidanceBias(…, ignore)`) — the plan's "suppressed against a bot's current combat target so it can close distance". Everyone else is still avoided, so a fight doesn't cause a pile-up. The corner speed limit still wins over hunting: nobody rides off the outside of a bend for a punch.
  - **A swing is thrown only when the predicted geometry says it will connect** — `wouldConnect` runs the same range-and-cone test as `CombatSystem.resolveStrike`, on where the target will be at the end of the wind-up (relative velocity × 0.1 s punch / 0.2 s kick). Punch if the punch reaches, kick if only the kick does, 65/35 punch when both would. The request goes through the identical `CombatSystem.request()` the P and K keys use; a bot has no reach, timing or force the player lacks.
  - **Win or whiff, the swing ends the engagement and starts a cooldown** (2.5 s at aggression 0.9, 8 s at 0.5; giving up a chase costs the same). This one rule is what keeps fights occasional rather than constant, and what makes an endless fight loop impossible — by the time a bot may want to swing again the road has separated them, and a knocked-off victim is 10+ s from remounting anyway.
  - **No fights below 30 km/h.** The first sim run had every knockdown happening on the grid in the first three seconds at walking pace — silly to watch, a huge cost to the victim for no skill, and a knocked-off rider standing next to a bike that hadn't gone anywhere. Fights are for the road.
  - **The player bias the plan asked for** ("so fights actually happen"): with the switch on, the player counts as 0.6× the distance when picking a target, and the engage roll is 1.6× keener against them. Without it, two of five seeds produced races where nobody went for the player at all.
  - `RiderPersonality.aggression` finally does something: it scales the engage chance, the patience alongside (2–4 s) and the cooldown. Viper (0.8) and Slugger (0.9) land most of the hits.
  - **The setting** is `AiCombatSettings` — `{ botsAttackPlayer: false, botsAttackBots: true }` by default — one object owned by `Game`, shared by reference with every bot's behaviour, so the checkbox takes effect on the next decision with nothing rebuilt. The panel is a plain DOM checkbox (bottom-right); it blurs itself after a change so the spacebar keeps pausing the game rather than toggling the box. The HUD reads it back, and hits by bots log as `[Phase 7]`.
- Hiccups / errors encountered:
  - **Chases expired at the moment the target arrived.** The engage timer originally ran from the moment a target was picked; a bot that picked a rider 9 m behind gave up 2–4 s later — exactly as they drew level. Now the clock only runs while the target is within 3.5 m along the road (waiting costs nothing), under an 8 s ceiling on the whole chase so a faster rider can't be followed down the road forever.
  - **A bot swinging at Slugger hit the player with the setting off.** The strike resolver auto-targets the *nearest* rider in the cone, whoever the bot intended; seed 11 caught it — zero chases at the player, one hit on the player. `CombatSystem.request()` now takes an optional `canHit` predicate carried through to the resolver, and bots pass their settings check with every swing.   - **The sim's stand-in player was unhittable.** The autopilot personality moves 3.5 m away from every bot it passes (avoidance), which no human does, and it was passing everyone at top speed — every chase at it was "lost". It now rides at mid-pack pace and carries an opt-out `dodges: false`, the one personality field added for this; every real bot leaves it unset.
  - Rescues within 30 s of a knockdown are reported separately and allowed, as in `sim:race`: a riderless bike thrown off a fast sweeper travels 40–80 m across the terrain band and off the world, and the rider remounts it there. The world-edge item under "Known, not blocking" in TODO.md, seen more often now that there are more knockdowns.
- Deferred items:
  - **Bots have no nitro.** Still player-only; belongs with the Phase 10 balance pass where it can be tuned against aggression.
  - **A remounted rider occasionally sits "stuck" on the road for 4 s** and gets rescued (one instance in five seeds, on the centreline, riding). Remounting does stand the bike upright, so it is likely facing backwards into the wrong-way block. Fall-system territory, Phase 10.
  - Bots choose punch vs kick on reach alone, with a fixed 65/35 preference when both reach. Aggression could weight the kick; left for the balance pass.
  - The sim's "occasional" band (>0 and <8 hits per minute) is a judgement; the user's browser verdict on whether 2–3 per minute *feels* right is what decides it.

### Combat tuning: shorter reach, a mandatory stand-off before a strike
**Status:** Done — confirmed headlessly (`sim:combat`, `sim:aicombat`, `sim:race`, `check:track` all pass; `build`/`tsc` clean)
Requested directly: riders were landing punches/kicks from further apart than felt right, and bots were swinging the instant they drew level, giving the target no chance to react and pull away. Two changes, both in the code shared by the player's P/K keys and the AI (`CombatSystem`/`AttackDefinitions` don't know which is which — see that file's own header comment):
- **Reach** (`src/combat/AttackDefinitions.ts`): `PUNCH.range` 2.3 m → 1.6 m, `KICK.range` 3.0 m → 2.1 m. `CombatBehavior`'s `STRIKE_LATERAL` (how far off a target's side a hunting bot positions itself) came down with it, 1.7 m → 1.3 m, so bots still reliably get within the new, tighter reach rather than parking just outside it.
- **A mandatory stand-off before a swing is even attempted** (`src/ai/CombatBehavior.ts`): once a bot is alongside its target (`STRIKE_GAP`), it now rolls a fresh random 2-5 s (`STRIKE_DELAY_MIN`/`MAX`) it must wait out before `tryStrike` is allowed to run at all — previously a bot swung the instant the geometry said a hit would connect, with no warning at all. The wait is *cumulative* time spent alongside, not one unbroken window — it pauses (doesn't reset) when the gap briefly wobbles past `STRIKE_GAP`, which happens constantly in a real race through corners and speed changes; only a genuine drop of the target (out of the hunting window entirely, patience running out, or the chase ceiling) clears it. `ENGAGE_SECONDS_MIN`/`MAX` (how long a bot stays interested before giving up) went from 2-4 s to 3-7 s and `MAX_CHASE_SECONDS` from 8 to 12, so a persistently aggressive bot's patience comfortably outlasts the new stand-off instead of expiring before it ever gets a swing in — without that, the delay alone would have made bots noticeably less effective than intended rather than just slower to commit.
- Hiccups / fixture updates needed (both were the existing regression scripts' own hand-picked test distances, calibrated against the old, longer ranges — not bugs in the new logic):
  - `scripts/combat-sim.ts`'s arc and closing-speed tests placed the victim at a fixed 1.8/2.0 m, inside the *old* punch range but outside the *new* 1.6 m one — every one of those probes started missing purely on range, masking what they were actually meant to test. Moved to 1.2 m, and along the way found a second, more interesting issue the tighter range exposed: at that separation the two riders' 2 m-long chassis boxes physically overlap for any bearing approaching 90°, and — even with velocity pinned to zero — Rapier's own penetration correction nudges the overlapping bodies apart mid-strike, which quietly shifted the measured bearing and flipped one boundary case (66°, just outside the 58° arc) from a correct miss into a false hit. This is a test-rig artifact, not a real gameplay condition (the AI positions bots almost directly to the side, near bearing 0, so it never manufactures this kind of near-head-on overlap) — fixed by disabling bike-bike collision for just these two synthetic riders, so the test's own stated intent ("geometry is the only variable") actually holds at the tighter range.
  - `scripts/ai-combat-sim.ts`'s third check — "bots attack you ON lands at least one hit on the player over two races" — started failing at the default seed: the mandatory stand-off makes landing a hit on any *specific* rider meaningfully rarer than before (by design), and two races' worth of samples, calibrated against the old instant-swing behaviour, wasn't enough to reliably clear that bar any more. Checked it wasn't actually broken by sweeping several seeds directly (3 of 6 landed a hit, 3 didn't — a real ~50% per-two-races rate, not zero), then widened the check from 2 races to 6, which reliably clears it while still meaning something (all 6 landing zero hits would be a real signal, not noise) — the isolated "two bikes pinned stationary and alongside for 15 s" plate test above it remains the deterministic proof the mechanism itself works.

### Manual transmission
**Status:** Done — confirmed headlessly (`sim:manual` new, `check:track`/`sim:race`/`sim:climb`/`sim:replay` against the named fixtures all unchanged; `build`/`tsc` clean); **pending user's look in the browser**
Requested directly: a real 6-speed manual option, modelled on actual geared-motorcycle dynamics (redline caps each gear until you shift up, lower gears pull harder and top out sooner), two shift keys, a mid-race toggle against automatic (like the existing autopilot toggle), and a choice on the start screen. Planned first (see the plan file this session referenced) specifically because of a real risk: `src/physics/Transmission.ts` already had almost exactly the right shape (per-gear top speed table, idle/redline RPM) but its own header comment said outright it was cosmetic-only — real drive force came from `VehicleController`'s one continuous torque curve, fully decoupled from gear. Every bot, and the player by default, needed that curve to come out of this change **byte-identical** — it's been through multiple hard-won tuning rounds earlier in this project (Phase 1/2's wheelie/toppling and steering fixes) and touching it for everyone to add a feature only the player can use would have been the wrong trade.
- Implementation notes:
  - **`Transmission.ts`** gained a `mode: "automatic" | "manual"` flag (default automatic, unchanged behaviour), `shiftUp()`/`shiftDown()` (manual only, real no-ops otherwise — confirmed by sim check 4 below), and `manualDrive(forwardSpeed, topSpeedScale)`, the actual physics model: unclamped per-gear RPM ratio (existing `rpmForGear`'s redline clamp is right for the display/audio it was built for, but the physics needs to see *past* 1.0 to tell "just hit the limiter" from "badly mismatched downshift"), a torque shape that ramps up off idle, holds through the midrange, and falls off hard in the last ~18% before redline (a rev limiter, not the automatic curve's smooth asymptote — at redline itself this is exactly 0, which is what makes a gear's speed genuinely plateau), a per-gear force multiplier (1.0 at 6th rising to 1.4 at 1st, so 6th gear peaks the same as automatic and low gears trade top speed for real extra pull), and — the consequence side — a threshold (8% past redline) past which the engine stops merely refusing to pull and starts actively fighting back with scaled engine braking, so a downshift two gears too low at speed costs real momentum rather than being harmlessly clamped away.
  - **`VehicleController.applyDrivetrain()`** gained exactly one new branch, `throttleInput > 0 && manual`, which calls `manualDrive()` instead of the existing continuous curve; every other branch (the automatic curve itself, braking, reverse creep, handbrake, finish brake) is untouched, character-for-character.
  - **Nitro** stays meaningful in every gear in manual mode: the automatic curve's boost extends one `topSpeedEstimate`, so manual mode passes the same proportional extension through as `topSpeedScale` on `manualDrive()` — without it, boosting in top gear would do nothing once that gear's own redline already capped speed at the un-boosted ceiling.
  - **HUD**: automatic mode is completely unchanged (gear number only, as before `G3`). Manual mode adds a percentage readout beside it (`G3 82%`), coloured amber past 85% and red past 95% of redline — a shift cue, not just a number, using the same two-stage falloff the physics itself uses so the colour changes exactly when the engine stops pulling as hard.
  - **Start screen**: a third card-picker block (`TRANSMISSION`, Automatic/Manual) mirroring the existing graphics-quality cards exactly, Automatic selected by default; `?transmission=manual` on the URL preselects it, matching the existing `?quality=`/`?track=` pattern. `T` toggles mid-race (bound in `Game.ts` alongside the existing `O` autopilot key, not dev-gated, same precedent) — switching into manual needs no gear re-sync, since automatic keeps the gear matched to road speed at every single step, so whatever gear is current the instant the key is pressed is already the correct one to inherit.
  - Bots are never given manual mode — `CombatBehavior`/`OpponentAI` never call `setTransmissionMode`/`shiftUp`/`shiftDown`, so every bot's `VehicleController.applyDrivetrain()` only ever takes the original, untouched automatic branch.
  - New headless sim, `scripts/manual-transmission-sim.ts` (`npm run sim:manual`), on a flat plate like `brake-probe.ts` (track geometry isn't what's under test): each of the 6 gears genuinely plateaus near its own top speed at full throttle rather than creeping toward the bike's overall ~40 m/s; shifting up out of a plateau resumes acceleration; downshifting from a plateaued 6th all the way to 1st produces real engine braking (38.0 m/s → 9.1 m/s over 2 s, throttle still held); and — the critical isolation check — an automatic-mode bike spammed with `shiftUp()`/`shiftDown()` every single step produces an *identical* gear sequence and *identical* final speed (to 1e-6 m/s) as one that's never called at all.
  - Hiccup found by the sim, fixed before it shipped: `manualDrive`'s torque ramp is exactly 0 at exactly 0 speed (`rpmRatio = 0/gearTopSpeed = 0`), which is a genuine fixed point — 0 force keeps velocity at 0 forever, in principle. The gear-plateau sim test happened to launch fine anyway (Rapier's own suspension-settling jitter was enough to nudge it off exactly 0), but that's luck, not a real guarantee, and launching from a genuine standstill is not a rare case here — it's the starting grid, held dead stationary by the handbrake through the countdown, exactly where a player would plausibly flip into manual before the lights go out. Floored the ramp at a small minimum (0.05) rather than true zero, and added an explicit exact-zero-velocity launch check (sim check 5) so this can't quietly regress.
- Deferred / not done this pass: no in-browser feel-testing (no browser automation connected this session) — the torque-shape constants (ramp/falloff points, the 1.4× low-gear bonus, the over-rev threshold/scale) are a first pass reasoned from how a geared motorcycle behaves, not dyno-matched or driven by hand; expect a tuning pass once the user has actually shifted through the gears.

### Minimap rebuilt: rotating heading-up map with real curvature
**Status:** Done — confirmed headlessly (`tsc`/`build`, `sim:flow`, `sim:race` unaffected); pending user's look
The first minimap (straight-line schematic, above) missed the point: "the map feature I wanted isn't like this!!" The actual ask — the real road curve, player fixed at the exact centre on *both* axes, the correct path pointing straight up from the player's dot, the whole map rotating as the road turns rather than the player moving on it — is a standard "heading-up" navigation map, not a relative-position radar, and needed real track geometry the first version deliberately avoided needing at all. Also: square, not a tall rectangle.
- **The rotation is two dot products, not an angle.** `Game.buildMinimapData()` hands `HUD.drawMinimap` the player's world position and current forward vector (X/Z, from `LOCAL_FORWARD.applyQuaternion(player.bike.worldQuaternion)` — the same pattern `debugKnockDown` already used for a world-space direction). Projecting a world-space offset onto that forward vector gives the screen "up" axis directly; projecting onto its perpendicular (`-forwardZ, forwardX` — this project's own `right = forward × up` convention, flattened to XZ, see `utils/Directions`) gives screen "right". No trig, no angle-wraparound edge cases, and it falls out of the same vector math the rest of the codebase already uses for everything else world-direction-related.
- **The road is real geometry now, not an assumption.** `buildMinimapData` slices `TrackDefinition.samplePoints`/`sampleRights` to a `±MINIMAP_RANGE` (200 m) window around the player's `distanceAlong` (`sampleIndexAt` finds the centre, `sampleSpacing` sizes the window in samples) and offsets each sample by the road's half-width each side — exactly the same "sample position + right vector × half-width" construction `TrackBuilder` uses for the real drivable road band, just without a collider. `HUD.drawMinimap` projects the left edges out and the right edges back into one closed path and fills it — a ribbon that actually bends when the road does, not a fixed-width rectangle.
- **Square** (`MINIMAP_SIZE = 180`, was a 130×260 rectangle), and — since it's a real proportional map now, not a stretched schematic — a single uniform scale drives both screen axes, so the curve's actual shape isn't distorted.
- Riders are now plotted at their real world position (`bike.worldPosition.x/z`) rather than reconstructed from `distanceAlong`/`lateralOffset`, projected through the same rotation as the road. The player's dot is still drawn last (never hidden under an overlapping rival) and still larger (`MINIMAP_PLAYER_DOT_RADIUS` vs `MINIMAP_DOT_RADIUS`), per the original request, which that part of the first version already had right.
